\framesubtitle{Linus Torvalds · April 2005}
\vspace*{\fill}
\begin{columns}[T]
\begin{column}{0.30\textwidth}
\roundedpic[0.97\linewidth]{figures/linus.jpg}
\vskip2.4mm
{\footnotesize\color{NovaBody}\emph{``I'm an egotistical bastard, and I name all my projects

\end{column}
\begin{column}{0.66\textwidth}
\vspace{2mm}
\begin{itemize}
  \item 2005. The Linux kernel: thousands of people mailing changes to one man — and the
    commercial tool that tracked them revoked its free licence.
  \item He wrote git himself, in about ten days, and was running the kernel on it two months
    later.
  \item Everyone holds the \textbf{whole history}. Every change is named by its contents, so
    nothing can be altered quietly. And it is \textbf{fast}.
\end{itemize}
\end{column}
\end{columns}
\vfill

\tanote{A minute, and it replaces the divider: the act opens on a person. The story, in the
order of the cards. 2005: Linus Torvalds has run the Linux kernel for fourteen years, thousands
of contributors, changes arriving by email. Since 2002 he had tracked them with BitKeeper, a
commercial tool that let the kernel use it free; in April 2005 that permission was withdrawn
after another kernel developer reverse-engineered its protocol, and the kernel had nothing.
Torvalds looked at the alternatives, decided they were all too slow ("take CVS as an example of
what not to do"), and wrote his own: first commit 7 April 2005, the kernel's own history moved
into it by June, the 2.6.12 release managed in git that month. Then the three design decisions,
which are the three ideas of the next eight slides: every developer has the entire history on
their own machine, not a copy of the current files — that is the local/remote slide; every
commit is named by a hash of its contents, so history cannot be rewritten without everyone
noticing — that is the record slide; and it had to merge and branch in seconds, because the
kernel did it hundreds of times a day. He handed maintenance to Junio Hamano within months and
has been a user since. The name: git is British slang for an unpleasant person; the quote is his
own joke about it. Then turn: here is how a change gets into main. If anyone asks about GitHub:
a company, 2008, that hosts git repositories and added the pull request; not the same thing.}

\tanote{Forty seconds, and say up front that it is an aside: nobody hits this today, because each
of them is alone on their own repo. It is here so the word is not new in Block 3, when they share
one. Point at the fork — both branches start from the same commit, and both change the same line
of logic.py. Feature-a
comes home first, so main moves. Then feature-b arrives with an edit to a file that no longer looks
the way it did when it left, and git stops. Be precise about when: it merges changes to different
files on its own, and it merges changes to different parts of the same file on its own; it refuses
only when the same lines changed on both sides. The fix is not a git command, it is a person
reading both versions and choosing. Say the reassuring half out loud, because the word frightens
people: a conflict is not a mistake, nothing is lost, and it is git declining to guess. How you
actually resolve one is Block 3 — GitHub Desktop shows both versions side by side and you pick.
What prevents most of them is already on the slides behind you: small commits, short-lived
branches, and pull before you start.}

\tanote{Ninety seconds, left to right. The dates are on the slide; the names and the story are
here. 1958, Rosenblatt's perceptron: a machine that adjusts its own weights from examples rather
than being programmed rule by rule. Still the whole idea. 1969, Minsky and Papert's book
\emph{Perceptrons}: one layer can only separate what a straight line separates, so it cannot learn
XOR. Funding collapsed; the first AI winter. Careful with the attribution: they wrote the critique
that made multi-layer nets the open problem, not the nets themselves. 1986, Rumelhart, Hinton
and Williams in Nature: backpropagation sends the error back through every layer, so many layers
finally become trainable. The answer to 1969, seventeen years late. Recurrence, two papers: Elman
(1990) gives a network memory of what came before; LSTM (1997) makes it survive a long sequence.
2017, Vaswani et al.: attention drops the chain — every word looks straight at every other, which
is why long text holds together and why it trains in parallel. Then the caption, which is the payoff: none of
this is new. What arrived was compute — CUDA in 2007 let ordinary programmers run their maths on a
graphics card, and in 2012 AlexNet trained on two of them and cut the ImageNet error by nearly half — and
data: Common Crawl, a non-profit giving the public web away as text. Neither is an idea about
intelligence. If someone asks why now and not in 1990, that is the answer.}

% ── persistent loop · the same controls, now across turns
\hue{NovaAccent}
\begin{frame}{The Ralph Wiggum loop.}
\vspace*{\fill}
\begin{center}\roundedpic[0.42\linewidth]{figures/ralph.jpg}\end{center}
\vskip3mm
\muted{Cheerfully wrong, and he gets there anyway. A loop around the loop: one run is one attempt,
and the same assignment comes back until the evaluation stops it.}
\vskip2mm
{\tiny\color{NovaMuted}The technique, and the name:
\srclink{https://ghuntley.com/ralph}{Huntley (2025), \emph{Ralph Wiggum as a ``software engineer''},
ghuntley.com/ralph}, a Claude Code plugin since Dec.\ 2025 · Ralph Wiggum from \emph{The Simpsons}
© 20th Television}
\vfill
\end{frame}
\tanote{This is a second loop around the agent loop they have just seen, not a smarter agent. Say
the distinction explicitly: the inner loop is read, edit, run inside one task. The outer loop
returns to the same assignment after a task ends. Both need the same three controls: a rulebook,
a judge, and a stop condition. The name is Ralph Wiggum because the process repeats the work
cheerfully until external evidence says it can stop. Huntley's original was a shell loop that fed
the same prompt file to a fresh agent each run; Anthropic shipped it as a Claude Code plugin in
December 2025 (`/ralph-loop "the assignment" --max-iterations 20 --completion-promise GREEN`: the
assignment, a cap, a phrase it may only say when true, and nothing checks the phrase, so the cap).
The next slide draws it, in the form they will actually type today.}

\begin{frame}{Persistent agentic loop.}
\vspace*{\fill}
\goalcmd
\vskip1mm
\ralphloop
\vskip2mm
\muted{The message stays fixed. The repo keeps the work. The eval decides whether it runs again.}
\vfill
\end{frame}
\tanote{Two minutes. Name the picture first: the Act 2 agent loop again, one level up --- the inner
loop is read, edit, run inside one task; this outer one returns to the same assignment after a task
ends. Walk the row: the agent works in the repo, which holds their rulebook, spec and tests; the
eval decides whether the goal is met, and today theirs is the test suite, which is why the judge
slide is where it comes from. On red the same assignment goes back in; the ghosts are the runs still
to come. The three tags are the point: the message never changes, the agent is told it again, the
repo keeps everything. Read the goal sentence aloud --- the spec's Done when, plus the fence and a
cap --- and say it is useful only after the red test exists. Then the trap, which is the judge slide
again: Codex stops "when it's confident it has reached the stopping condition", its own word, so the
finish line must be something it shows, the test output on screen. (Claude Code's version has a
second model read the thread each turn; it cannot run the tests either, which is what the cap is
for.) The boundary: a goal persists; it does not create the rulebook, the judge or the human review.
Say the setup aloud, as it is no longer on the slide: once, `codex features enable goals`, restart,
then /goal plus the sentence in a new thread --- both written out on the Week 4 page.}
