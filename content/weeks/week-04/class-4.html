Standard 1 · The rulebook

AGENTS.md — the file it reads first.

What it is

A README for agents

Codex reads it at the start of every session, before anything else. So do twenty other tools. Your repo has had one since Class 2.

What goes in

Only what it can't guess

Commands (uv run …). Boundaries (never edit tests/). Etiquette (branch named after the spec). How to report (paste the test output).

What stays out

Anything it can read

Explanations of the code. Tutorials. "Write clean code." Every extra line hides the important ones.

It is code: in git, reviewed, pruned. When the agent misbehaves, the fix is usually one line here — not a longer prompt.

Ask Codex on stage: "What does AGENTS.md tell you to do?" — it recites the file. That's the proof it reads it. The test for every line: would removing it cause a mistake? If not, cut it. Mention the 32 KB cap only if asked; the real cap is attention.
Standard 1 · Live · 5 min

Three lines. One commit.

Open AGENTS.md in your repo. Under How to answer, add:

- Build each spec on a branch named after it, e.g. feature-2-categories. Never commit to main directly.
- After every change, run the tests for the task and paste the final output. The output is the proof, not a sentence.
- Never edit, delete or skip anything in tests/. If a test looks wrong, say so and stop.

GitHub Desktop → AGENTS.md changed → summary "AGENTS.md: rules for building features" → Commit to main → Push.

Do it on stage first: ask Codex "Add these three lines under How to answer in AGENTS.md", read the diff, accept. Then commit in GitHub Desktop. Point out the last one already existed in spirit ("never edit tests") — now it's explicit and it's a rule the student enforces. Codex picks the new rules up on the next thread, not mid-thread: say "new thread" now.
Standard 2 · The judge

Define done before you build.

Something that can't lie

The agent stops when the work looks done. Give it a check that says pass or fail: the spec's Done when and tests/test_feature_2.py. Four red tests are your to-do list.

Never move the goalposts

An agent that edits a test to make it pass has cheated, not finished. The rule is in AGENTS.md. You enforce it.

Evidence, not claims

"All tests pass" is a sentence. The test output is evidence. Ask for it every time.

Green is not the end

The judge checks what it was told to check. After green: read the diff, click the app. App wrong, tests green? Write down what the judge missed — that's a test that should exist.

Run the red tests on stage: uv run pytest tests/test_feature_2.py → 4 failed, "logic has no attribute CATEGORIES". Open the test file and match each test to a checklist line in the spec, like last week. The "green is not the end" card matters today: feature 2's selectbox in the form isn't tested at all — only clicking the app catches a missing one.
Standard 3 · The loop

Red → build → run → read → fix → green → stop.

One task per loop

One bug, or one spec. Not "fix everything you see". The rule is in the file; the prompt names one file.

Let it loop

Tell it to run the tests after every change and keep going until green. It reads the failure and fixes it. You read the result, you don't relay errors.

A stop condition

Green — or a cap. Same failure twice: stop, read it yourself, new thread, better prompt. A clean thread beats a long one full of corrections.

Today the loop runs inside one Codex turn and you watch. The same idea one level up is a script that re-feeds the prompt until the judge passes — the "Ralph loop". Part II.

The three parts are the whole lesson: a rulebook, a judge, a loop. Everything else in agentic coding is a variation. Don't demo the bash loop today unless a laptop has Codex CLI and you have five spare minutes at the end — it's a spectacle, not the lesson.
Standard 3 · The prompt

The loop prompt.

Build specs/feature-2-categories.md. Work only on the branch feature-2-categories. After every change, run uv run pytest tests/test_feature_2.py and keep going until all four tests pass. Do not edit anything in tests/. When they pass, paste the final test output and list every file you changed.

The task

One spec, by file name.

The boundary

One branch. No tests/.

The judge

The test command, every change.

The evidence

Output + file list.

Four parts, in every loop prompt you ever write: the task, the boundary, the judge, the evidence. Students copy it from the Week 4 page and change two file names. New thread before pasting — the AGENTS.md lines from five minutes ago are only read at thread start.
Class 4 · Live · Feature 2 · 13 min

Watch it loop. Then don't trust it.

1Branch. GitHub Desktop → New branch → feature-2-categories.
2Red. uv run pytest tests/test_feature_2.py → 4 failed. The to-do list.
3New thread. Paste the loop prompt. Watch: it edits, runs, reads a failure, edits again. Don't touch anything.
4Green. Read its output: four passed? Every file it lists?
5Read the diff. Three places must change: COLUMNS in db.py, every line of seed/expenses.csv, then uv run python seed.py. Did it run seed? Did it touch data/ by hand?
6Click the app. Add expense → is there a category box? Group page → totals per category? Not tested — only you catch it.
7Commit, push, PR, merge. Like last week.
Let it loop for real; it usually takes 2–4 rounds. Narrate what you see: "it ran the tests — two still red — it's reading the failure — it edited seed/expenses.csv". The two things it commonly misses: forgetting to run seed.py (data/ still has no category column → the app crashes on load while the tests are green, because tests use fresh_data from seed/) and no selectbox in the form (nothing tests app.py). Both are the "green is not the end" lesson — don't fix them silently, show them. If it edits a test: stop, discard, point at the rule, re-prompt.

Class 4 · When the loop goes wrong

Five things you'll see.

1It edited a test. Discard that file in GitHub Desktop. "Never edit tests/." Run again.
2It says done, tests are red. "Paste the test output." The output is the judge, not the sentence.
3Same failure three times. Stop. Read it: last line says what, the line above says where. New thread, better prompt.
4It fixed three other things too. Discard them. One task per loop. Ask again for the one thing.
5Green, but the app is wrong. The judge missed it. Write down what. Re-prompt with the symptom, or fix by hand.

Every row is a line for your AGENTS.md. Keep the list.

Class 4 · Retro · 7 min

What did it get wrong? Write the rule.

  • In your group: the worst thing the agent did today. One sentence each.
  • Turn it into a rule. Short, specific, testable. "Run uv run python seed.py after changing anything in seed/."
  • Add it to AGENTS.md. Commit: "AGENTS.md: <the rule>, because <what happened>". Push.
  • Three groups read theirs out.

That is how the rulebook grows: from what went wrong, one line at a time. Not from a longer prompt.

Collect the rules on the board; the good ones become the course's AGENTS.md for Block 2. Expect: "run seed.py after seed changes", "don't touch data/", "show me the diff before you commit", "one file at a time". Reject vague ones ("be careful") — ask "how would you know it followed this?".
